# 调查与 Context 状态简化：设计方案

状态：已收敛的设计方案，运行时尚未实施。初始讨论：2026-10-29；最新审查与决策：2026-10-30。

正文第 1–13 节是当前唯一实施方案：移除调查领域数据模型，依靠 Pi messages 与工具结果推进诊断，保留应用执行控制。架构现在即按单一 Session、禁止历史导航和 reload/rebind 设计，不保留这些路径的兼容与恢复机制；命令禁用的入口实现独立后续交付，不阻塞本次简化。

本文不声明运行时行为已经改变，也不替代现有阶段的验收记录。实施时同步更新 `AGENTS.md`、`docs/DESIGN.md` 和相关契约；当前代码及历史验收仍按既有行为解读。此前第 1–9 节讨论移至末尾历史附录，不能作为实施步骤。

## 1. 目标与职责

用户提出的新方向是：不要 `domain` 中的调查数据结构，调查过程尽量向 HolmesGPT 的模型消息与工具结果循环靠拢。不再并行维护对话历史与结构化调查聚合，也不要求模型为记录判断而调用额外的领域写工具。

```text
用户提出问题
  → 模型根据 messages 判断下一步
  → 调用 Kubernetes MCP 工具
  → 结果进入 messages
  → 模型根据新证据继续查询、修正判断或向用户提问
  → 模型生成最终报告
```

职责分配：

| 所属方                | 职责                                                                               |
| --------------------- | ---------------------------------------------------------------------------------- |
| Pi                    | 维护 messages、运行 agent/tool 循环、处理上下文压缩与对话持久化                    |
| LLM                   | 提出和修正假设、解释工具结果、判断是否需要继续取证或询问用户、决定何时给出最终报告 |
| Pi SRE                | 管理当前集群选择、MCP 连接与工具、只读策略、参数校验、请求取消及调用限制           |
| Kubernetes MCP Server | 执行 Kubernetes 查询                                                               |

调查仍然是一种用户任务和模型工作过程，但不再是应用必须维护的独立领域实体。移除数据结构不代表移除参数类型、工具协议类型或运行状态类型，也不意味着直接删除整个 `src/domain/` 目录而忽略其中被其他模块使用的逻辑；实施时按职责迁移必要校验。

## 2. 移除的模型与配套机制

不再独立维护 `Incident`、`InvestigationState`、`InvestigationScope`、`Target`、`Evidence`、`Hypothesis`、`Conclusion` 和领域 `OperationOutcome`。查询来源和必要执行信息直接保留在工具结果中，不另建调查记录。

相应移除：

- `sessionId → incidentId` 映射、调查 binding、incident lifecycle epoch、不可变 incident scope 与 effective/next 转换。
- EvidenceStore 及其证据 ID、领域证据引用校验、假设状态校验、调查与 hypothesis revision。
- `hypothesis_upsert`、`investigation_conclude`、`investigation_get`、`evidence_list` 和 `evidence_get` 模型工具。
- `/incident`、`/evidence` 及基于领域状态的调查检查界面。
- pending conclusion、`agent_end` 结论提交和终态禁止继续查询的调查生命周期机制。
- `createInvestigationScopeDescription()` 及持续向 messages 同步领域摘要的机制。
- 独立的调查 `environmentEvents` 列表、结构化调查 JSONL 归档及其容量释放流程。

上述是后续实施方向，不表示当前代码已删除这些功能。既有历史文档和验收记录仍描述当时实现。

## 3. Messages 是调查过程的记录

查询结果直接作为 tool result 进入 messages；模型在后续消息中修正解释，不需要创建或更新 Hypothesis 对象。用户补充信息也直接进入同一对话，无需应用维护 `investigating`、`waiting_for_user` 或其他调查状态。

每条 Kubernetes 工具结果都在模型实际可见的 `content` 中明确实际 context、操作、必要的 namespace、查询时间、成功或失败及截断情况；不能只把来源放在 `details` 中。成功、失败和取消使用一致的来源表达，失败查询不能伪装成空结果或成功观察。未派发调用明确标为未执行，不编造查询时间；已派发调用保留派发和收尾时间。namespace 省略时标明由 server/context policy 决定，不宣称已覆盖所有 namespace。来源信息应在结果大小限制内完整保留，无法容纳时在派发前拒绝，不截断或改写 context 身份。

结果脱敏、大小和截断限制由工具结果管线负责，不依赖 EvidenceStore。本次继续关闭原始响应保留，不新增临时文件存储、原始结果读取入口或保留/清理机制。大响应仅提供受限、脱敏的结果；不承诺后续能够取回被截断部分。

已有工具结果及模型消息包含的证据与判断，不再通过 evidence/hypothesis ID 摘要重复注入。当前集群选择、MCP 可用性和有意义的环境变化仍需通知模型，因为它们可能在对话之外变化；通知来自实际运行状态，不能仅凭 messages 获得执行权限。

环境变化直接记录为应用消息，不同时维护一份领域事件列表。通知包括用户改选、inventory 增删、同名 context 的 server 指向变化，以及 MCP 断开和恢复。内容相同的刷新不重复通知；default 标记仅作展示元数据，不改变选择。环境更新和消息来自同一事实，消息不暴露凭据、server 地址或原始敏感数据。

沿用 steering 通知能力；压缩后、下一次模型请求前补充当前必要的运行环境，包括当前选择、可用目标、unavailable selected、MCP 状态和必要的目标变化提示。自动 compaction 后可能直接续跑，不能只依赖 `before_agent_start`；实施时必须覆盖这条路径，并对相同快照去重。历史观察的 context 和时间不得因当前环境变化而改写；同名目标指向变化后不能把旧观察当成新目标的当前事实。

历史调查内容由 Pi 的 compaction 尽量保留，但不保证无损或严格证据关联。压缩后缺少关键来源或事实时，模型应说明限制并按需重新查询，不重建另一套调查聚合。应用不从 transcript 恢复执行权限或领域状态。

## 4. 最终报告与调查结束

LLM 决定何时已经能够回答、需要用户补充，或只能给出信息不足的结论。最终自然语言回答就是调查报告，不需要额外调用 conclude 工具，不需要应用写入 `resolved` 或 `inconclusive` 终态。

本方案取代附录中的“直接提交结论”方案：不仅移除延迟提交，也移除结论提交本身。应用不判断根因是否充分，不校验结论必须引用某个 supported hypothesis。只读、调用范围和运行条件仍由应用执行校验。

模型给出报告后，用户可以在同一对话中继续补充、追问或要求重新查询；不需要重新打开 Incident。`agent_end` 不承担调查状态迁移，也不能直接等同于用户请求最终收尾；请求边界见第 8 节。

需要机器处理的结果时，可以在最终输出阶段要求模型按约定 schema 生成报告；这不要求调查过程中维护对应对象。是否提供固定报告 schema、导出命令或额外总结步骤，仍是待定产品需求，本次不新增。

## 5. 保留的执行控制状态

移除调查领域模型不等于移除应用执行状态。保留并由对应模块直接拥有：

- MCP 连接、工具发现、ready 状态、重连与关闭处理。
- 当前 available contexts、用户的 all/exact 选择及调用时的可用性计算。
- 每次调用显式提供一个准确 context；应用校验后原样传递，不推断、注入或覆盖。
- 诊断工具 allowlist、参数校验、只读配置与 RBAC 边界；不增加 shell 或 kubectl 绕过路径。
- 请求身份、排队与活动调用跟踪、取消信号、超时及资源释放。
- 工具结果的来源、错误分类、脱敏、大小和截断限制。
- 防止旧连接调用被隐式转移到新连接或重放的连接身份（可使用内部 generation）、取消信号及工具/环境发布屏障；明确保留这些保护，归 MCP 生命周期及应用协调层所有，见第 11 节。
- 必要的调用与资源预算，但预算不再挂在 Incident 上。

调用在接收时固定 context，后来改选不撤销已接收调用，具体规则见第 10 节。调用直接按自身身份和来源返回结果；显式取消或旧连接失效的调用不得作为新的成功结果发布。

## 8. 已确认：采用 HolmesGPT 的对话与请求边界

诊断不要求存在活动调查，不需要用户先创建 Incident，也不在首次查询前自动创建。应用收到用户问题后，模型直接根据 messages 分析，并在当前只读策略、集群选择和 MCP 运行条件允许时调用诊断工具。

同一对话中，追问、补充信息、重新检查和切换话题都通过追加用户消息表达。LLM 根据历史理解问题之间的关系，但不负责识别、创建或切换 Investigation 实体；应用也不维护“当前调查”或“新调查”的状态。模型给出报告后仍可继续查询，无需重新打开调查。调查的语义边界不决定执行权限、调用归属或预算。

调用与结果的归属：

- Pi 对话承载多轮 messages；每轮用户请求拥有独立的请求身份，每次具体工具调用保留自身调用身份和实际 context。两者是执行关联信息，不是新的调查领域对象。
- 工具调用在接收时固定所属请求、准确 context 和必要参数，后续 context 改选不能改写其来源。结果返回原调用，不转移给后续用户请求。
- 受限、脱敏的工具结果直接进入 messages，保留操作、来源、时间、成功或失败及截断信息。已有结果可用于后续追问，不创建独立 EvidenceStore 或 evidence ID。
- 对话持久化由 Pi 负责。本次不保留原始响应，不新增大响应外部存储；messages 中仅保留受限、脱敏的工具结果，不承诺截断或压缩后能够访问完整原始结果。

已确认采用最简运行方式：follow-up 固定逐条处理（`one-at-a-time`），不把多条排队用户消息合并为同一请求；用户设置不能把这条执行规则改回批量处理。每条在实际开始处理时获得独立请求身份和额度，排队本身不创建活动请求或占用额度。这里的逐条处理指用户请求，单个请求内的诊断工具仍可受限并行执行。

| 输入或运行事件                                         | 请求身份与额度                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------ |
| 空闲时开始处理有效用户问题                             | 新请求、新额度；被命令或输入处理器消费的输入不创建请求             |
| 活动期间用户 steering                                  | 归入本轮，不重置额度                                               |
| 排队的用户 follow-up                                   | 本轮工作收尾后逐条取出；每条实际开始处理时创建新请求、新额度       |
| 应用环境 steering                                      | 不创建请求或额度；空闲时仅追加环境消息                             |
| 模型工具循环、自动续跑、模型重试、compaction、MCP 重连 | 保留本轮身份和剩余额度                                             |
| 显式取消                                               | 结束本轮执行归属并取消所属调用；下一条开始处理的用户问题使用新身份 |

Pi 的 follow-up 可以在同一个底层 agent loop 中被取出，不一定再次触发 `before_agent_start`；`agent_end` 后还可能自动重试、压缩或续跑。因此不能简单以这两个事件重置预算。`agent_settled` 可用于最终运行清理，但也不能据此识别同一 loop 内的所有 follow-up 边界。实施时应在逐条用户消息实际被处理、下一次模型请求开始前明确切换请求归属，并验证取消与自动续跑事件顺序。

请求状态仅保存执行身份、预算、取消信号和活动调用等运行信息，不保存问题语义、假设、结论或调查生命周期，不演变为新的 Investigation。

预算与请求收尾：

- 每轮用户请求获得独立的诊断调用额度，无论它是旧问题的追问还是新话题。应用不要求 LLM 分类后才决定是否重置预算。
- 同一请求中的模型迭代、工具循环、自动续跑、compaction、重连及重试不重置额度。Steering 环境通知本身不创建新一轮请求或新额度；运行中追加的用户 steering 也沿用本轮额度。排队作为下一轮处理的用户消息，在开始处理时获得新额度。
- Pi SRE 继续限制实际 MCP 诊断 dispatch 次数：排队和派发前拒绝不消耗额度，紧邻实际派发前同步扣减；已派发的失败、超时或取消不返还额度，重试再次派发另计。并行调用共享本轮上限。
- 达到调用上限后拒绝进一步诊断派发，模型仍可根据已有结果回答并说明限制。预算耗尽不是调查终态；用户下一轮提问可以继续。
- 正常完成本轮前，应完成该轮已接收请求的收尾。显式取消覆盖排队与已派发请求：停止排队派发并尝试中止执行，迟到结果不得作为新的成功结果进入当前对话，仍按原请求完成资源释放。新一轮请求不接管旧请求或其剩余额度。旧调用必须返回匹配的错误/取消工具结果并释放资源，不能让对话中的工具调用悬空，也不能重复发布迟到结果。
- Dispatch 上限只限制实际 Kubernetes 查询，不足以限制模型反复提交无效参数、越界调用或预算耗尽后的重试。运行层另设本轮模型迭代上限，覆盖这些不消耗 dispatch 额度的循环；阈值在实施时配置并测试，不依赖提示词自行停止。自动续跑、重试、compaction 和环境通知不能重置该限制，达到上限后停止进一步自动运行并向用户说明已有结果和限制。

这里借鉴 HolmesGPT 的是“不依赖活动 Incident、以 messages 延续分析、按请求限制执行”的边界，并非照搬全部实现。HolmesGPT 的 `max_steps` 限制模型迭代，一次迭代可以并行调用多个工具；Pi SRE 保留实际 MCP dispatch 次数上限。HolmesGPT CLI 在同一问题的审批恢复中延续迭代计数，但不能据此认为所有 HTTP 跨请求续跑都自动共享预算；Pi SRE 的本轮续跑规则由应用显式落实。

核对依据固定为 HolmesGPT 提交 `257ecf3f374a0e283405b58c28baf22dba6a87ae`：

- [CLI ask](https://github.com/HolmesGPT/holmesgpt/blob/257ecf3f374a0e283405b58c28baf22dba6a87ae/holmes/main.py#L409-L449)：直接运行 agent，回答后才构造用于结果处理的 Issue。
- [Chat 请求模型](https://github.com/HolmesGPT/holmesgpt/blob/257ecf3f374a0e283405b58c28baf22dba6a87ae/holmes/core/models.py#L237-L261)：业务来源和 conversation ID 为可选关联。
- [交互请求循环](https://github.com/HolmesGPT/holmesgpt/blob/257ecf3f374a0e283405b58c28baf22dba6a87ae/holmes/interactive.py#L2565-L2663)：用户消息追加到历史，每次用户输入从零开始计算迭代，同一问题的审批恢复延续计数。
- [Agent 循环](https://github.com/HolmesGPT/holmesgpt/blob/257ecf3f374a0e283405b58c28baf22dba6a87ae/holmes/core/tool_calling_llm.py#L1266-L1284)：`max_steps` 限制模型迭代，最后一轮不提供工具。
- [对话导出](https://github.com/HolmesGPT/holmesgpt/blob/257ecf3f374a0e283405b58c28baf22dba6a87ae/holmes/interactive.py#L2191-L2213)与[大结果临时存储](https://github.com/HolmesGPT/holmesgpt/blob/257ecf3f374a0e283405b58c28baf22dba6a87ae/holmes/core/tools_utils/filesystem_result_storage.py#L25-L70)：messages、工具历史和临时原始结果具有不同的保存边界。

## 9. 已确认：Exact 选择保留 unavailable selected

用户的 exact 选择表达持续的选择意图，与当前 inventory 的可用性分开维护。已选 context 从 inventory 消失时，仍属于 exact 选择，并在选择器、状态展示与模型环境摘要中标为 **unavailable selected**；不自动取消选择、不替换名称，也不回退为 `all`。

对于后续新接收的调用：

- 当前可执行目标集合为 `exact selected ∩ available contexts`；工具能力、MCP 就绪状态和其他执行限制仍需满足。
- 交集中的 context 可以继续查询；对 unavailable selected 的调用在派发前拒绝，明确说明目标已选择但当前不可用。
- 交集为空时保留完整 exact 选择并阻止诊断调用；不隐式选择其他 context。
- 消失的 context 重新出现在有效 inventory 中时，只要用户尚未将其移出 exact 选择，就自动恢复为可执行候选，无需重新选择。恢复可用不表示认证成功、健康或已经检查，也不重放此前失败或中断的请求。
- 新出现但不属于 exact 选择的 context 仍在范围外。仅用户显式改选才改变选择意图；选择器必须保留 unavailable selected 项，允许用户明确取消它们，应用选择时不得静默丢弃。

例如，exact 选择为 `{A, B}`，inventory 从 `{A, B}` 变为 `{A, C}` 后，选择仍为 `{A, B}`：A 可执行，B 为 unavailable selected，C 在范围外。B 恢复后自动回到可执行候选；若用户已取消选择 B，则不会自动选回。

以上针对已选 context 的运行时消失与恢复，不改变启动时未知 exact 名称的校验规则。已接收调用仍遵循第 10、11 节：用户改选不撤销请求，但排队请求在派发前必须检查原目标的当前可用性，不能替换 context。

## 10. 调用接收与实时改选

应用收到具体工具调用后，同步校验当时的用户选择、工具能力、准确 context 和可用性，并登记所属用户请求、工具调用身份、实际 context、必要参数及连接身份。校验与接收登记之间不插入异步等待；登记后进入等待队列即为已接收调用。

```text
收到调用 → 校验并登记归属/context/连接 → 排队 → 检查运行条件 → 扣减额度并派发 → 收尾
```

- 新选择只影响此后新接收的调用。已接收调用不因用户改选而撤销，也不重新按后来的选择授权。
- 排队调用派发前仍检查取消、所属请求、原连接是否有效、工具能力和原目标可用性；排队不保证必定执行。不能替换 context、连接或同名 context 的实际目标。
- 基于旧选择生成、但在改选后才到达应用的调用，按新选择校验；拒绝时说明当前范围或可用性，不自动改写参数。
- 用户改选与连接替换分别处理：改选保留已接收调用，旧连接失效则按第 11 节中断其活动和排队调用。
- 显式取消覆盖排队和已派发调用，迟到结果不得成为新的成功结果；调用按原身份完成取消收尾，不归到后续请求。

例如，选择 A 时接收了对 A 的调用，用户随后改选 B；只要原连接、工具和目标仍有效，该调用仍查询 A，结果明确标注 A 及时间。改选后新接收的调用按 B 校验。

## 11. MCP 手动恢复与连接替换

### 11.1 触发方式与保护归属

沿用当前触发方式：应用启动时自动连接；运行中断线后标为不可用，由用户运行 `/mcp_restart` 恢复，不新增后台自动重连循环。普通命令保留健康连接，`/mcp_restart --force` 即使连接健康也替换连接。以后若增加自动恢复，也必须复用同一连接替换协议。

保留连接身份/内部 generation、取消信号以及发布屏障，收回 MCP 生命周期和应用协调层；不再传播到调查领域对象。MCP 连接取消与整个 AgentSession 的取消分开，断线本身不取消整段对话。工具列表、输入 schema、能力及 inventory 均可能变化，不假定重连前后相同。

### 11.2 替换协议

1. 关闭 dispatch 并撤下旧工具，阻止新的 Kubernetes 查询。
2. 使旧连接失效，中断其活动和排队调用；每个调用明确收尾，不迁移到新连接、不隐式重放。
3. 建立新连接，重新发现工具/schema 和 inventory，按用户未变的 all/exact 规则计算可用目标。
4. 发布匹配的工具、可用目标及环境通知，再开放 dispatch。通知在活动运行中按消息顺序交付给模型，不等待模型确认才开放执行。

发布由应用协调层完成，不要求底层 MCP transport 独自管理用户选择和 Pi 工具注册。发现或发布失败时保持受影响的诊断调用关闭，不回退到旧工具或旧 inventory。旧 schema 生成的调用不能直接执行，必须由当前工具及其校验规则处理，不兼容时明确拒绝。

同名 context 的 server 指向变化属于实际目标变化；通知中标明目标已变化，但不暴露原始地址。历史观察继续保留来源和时间，旧排队调用不能仅因名字相同就查询新目标。连接替换已中断全部旧调用，恢复后由模型重新决定查询。

### 11.3 中断结果与对话继续

| 调用状态         | 返回与保留                               | 本轮 dispatch 额度 |
| ---------------- | ---------------------------------------- | ------------------ |
| 已完成并发布成功 | 保留原工具结果，作为历史观察             | 保持已消耗         |
| 已派发但未完成   | 尝试中止，返回“连接中断，未取得有效结果” | 不返还             |
| 排队尚未派发     | 移出队列，返回“连接中断，未执行”         | 不扣减             |
| 旧连接迟到结果   | 不发布为成功，不重复收尾，只释放剩余资源 | 不改变             |

这些中断结果返回原工具调用，带准确 context、操作、执行状态和适用时间；不能伪装为空查询或成功。撤下工具不能使已接收调用的结果悬空。

例如，Pod 查询已成功、日志查询执行中、事件查询排队时断线：保留 Pod 结果，日志返回未取得有效结果，事件返回未执行。模型可以基于这些 messages 解释已知情况、指出信息缺口并提示恢复 MCP，无需结束或重建调查。

- 恢复时本轮仍在运行：发布工具和环境通知，模型在后续处理点可发起新调用，沿用本轮剩余额度。
- 本轮已回答并收尾：恢复命令仅更新工具和环境，不自动启动模型或恢复诊断任务。用户说“继续检查”时作为下一轮处理，获得新额度并沿用已有 messages。
- 恢复后重查属于新调用，重新校验当前 schema、选择和可用性，按实际派发扣减调用额度；恢复本身不重置本轮额度。

## 12. 单一 Session 架构与后续入口禁用

已确认：**架构现在就按相关能力已禁用的前提设计，只有入口禁用的实现推迟。** 整个应用运行期使用同一个 `AgentSession`，不支持会话替换、历史回退/分支切换或运行时扩展 reload/rebind。扩展只在启动时初始化一次、退出时释放，修改扩展通过重启应用生效。模型回答结束后仍沿用原对话，追问和换题通过用户消息表达。

因此，本次简化直接删除 session 与调查映射、binding/epoch、会话恢复、分支恢复、扩展重新绑定与状态重新挂接等机制。不为尚未关闭的上游入口保留过渡兼容代码、恢复流程或相关测试，也不重建新的运行时绑定权限层。

命令、快捷键和程序入口的实际拦截单独后续交付，覆盖 `/new`、`/resume`、`/fork`、`/clone`、`/import`、`/tree`、`/reload` 及对应操作。入口禁用推迟不代表这些路径继续属于简化架构的支持范围；尚未实现拦截也不能宣称禁令已经由运行时强制执行。入口禁用交付前的开放路径是已记录的产品交付缺口，不通过维护旧功能兼容机制填补。

正常请求取消、工具结果收尾、超时、活动调用跟踪、应用退出时的订阅注销与资源释放仍保留。它们服务于正常执行生命周期，不承担会话切换或 reload 恢复。Compaction、用户 steering、context 改选及 MCP reconnect 继续保留；MCP reconnect 只替换连接和工具，不重建扩展。

### 12.1 现有状态的删除与最小替代

| 现有机制                                                   | 简化后的处理                                                                                        |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `sessionId → incidentId`、应用调查 binding                 | 删除；Pi 自身的 session ID 和对话持久化属于 Pi，不要求修改 Pi 内部实现                              |
| `bindingEpoch`、incident `lifecycleEpoch`、`scopeRevision` | 删除，不保留会话切换、扩展重绑或调查终态的代次保护                                                  |
| `selectionRevision`、`inventoryRevision`                   | 删除用于调用授权和结果失效的版本组合；选择器只保留必要的草稿校验，不因此保留全局执行版本机制        |
| 调查 controller 的 `toolsGeneration`                       | 随 controller 删除；MCP 层保留一种连接身份保护（连接对象或内部 generation），不重复维护调查工具代次 |
| `workEpoch`、用于阻止改选的 active work 集合               | 删除；只保留调用队列和活动调用跟踪，用于并发限制、取消及收尾                                        |
| `validatedSelection`                                       | 分离启动名称校验和运行时交集计算，不保留混合两种职责的状态标记；运行时保留 exact 选择意图           |
| `inventoryTransition`                                      | 不保存调查事件列表或独立的最近变更状态；刷新时计算必要差异并发送应用消息                            |
| execution snapshot / incident lease                        | 删除复合权限快照及比较机制；只保留调用身份、所属请求、准确 context、参数、连接身份和取消信号        |
| `publicationBlocks`                                        | 保留发布屏障语义，合并为 MCP 运行状态中的未就绪阶段，避免额外维护多层发布计数/权限机制              |

保留的是执行所需的最小事实和控制，不是把被删除的 epoch/revision 换名重新引入。全局环境变化不再作为已接收调用结果失效的统一条件；取消、原连接失效和原目标不可用仍按第 10、11 节处理。

### 12.2 后续命令禁用的交付边界

后续单独确定 Pi 的统一 command/action policy 接口和上游或受维护依赖版本的交付方式，覆盖补全、帮助、选择器前置逻辑、快捷键和程序入口。该功能负责落实既定架构约束，不要求先保留一套支持会话切换或 reload 的应用架构再二次删除。

配套审查见 [TUI 内置命令的隐藏与禁用](./TUI_COMMAND_VISIBILITY_AND_RESTRICTIONS.md)。本方案移除 `/incident`、`/evidence` 属于调查模型删除，与后续禁用 Pi 内置命令分开交付。

## 13. 验收重点

- 多轮追问、用户补充和新证据修正判断，仅通过 messages 延续，不创建 Incident 或调用领域写工具；回答后仍能查询。
- 多条 follow-up 逐条开始并各得新额度；steering、自动重试、compaction、重连和自动续跑不重置本轮额度。单轮并行调用共享上限，派发失败不退款，未派发拒绝不扣减。
- 重复无效调用和预算耗尽后的模型循环受到运行层迭代上限约束，不无限续跑。
- 改选时排队调用保留原 context；改选后新调用使用新选择校验。Exact 项消失、恢复及全部不可用时保持选择意图，不静默扩大范围。
- 断线和强制替换同时覆盖已派发与排队调用，返回不同中断结果；旧连接迟到结果不发布成功，工具调用不悬空。重发现 schema/inventory 并完成工具与通知发布前不能 dispatch。
- 对话仍在运行时可在恢复后继续；已收尾时恢复不自动启动模型，用户明确继续后使用新一轮额度。
- A、B 集群有同名 Pod，经过 context 改选、server 指向变化和手动/自动 compaction 后，模型仍区分历史观察来源，按需重新查询。自动压缩续跑的下一次模型请求包含当前环境。
- 成功、失败、取消、截断和 namespace 省略的来源在模型可见内容中明确；脱敏及结果上限持续有效，不新增原始响应或临时文件留存。
- 按单一 Session、扩展仅初始化一次验收；不为会话替换、分支导航、reload/rebind 保留兼容与恢复机制。正常请求取消、MCP 重连及退出清理仍有效；入口禁用属于后续单独验收，不算作本次已实现能力。

本次仅更新设计文档，不实施以上运行时变更。

## 附录：此前设计讨论（非实施要求）

以下保留此前第 1–9 节原讨论，便于理解当前复杂度来源。段落中的“已确认”“待定”及章节编号均属于当时版本；涉及 Incident、环境事件列表、直接 conclude、重连待定，以及“先禁用命令再删除领域 binding”的要求均已由正文取代。正文第 7 节是唯一实施顺序，不执行这些中间方案。

### 历史 1. 目标与设计方向

调查的核心流程应该是：提出问题 → 查询 → 留存证据 → 更新假设 → 得出结论。

目前连接与 context 的过渡状态进入了执行授权、证据提交、工具发布和调查生命周期，增加了核心流程的复杂度。希望将环境变化主要作为调查背景保留，而由人决定是否继续、重新检查，或者重新开始调查。

本次讨论提出的方向：

- Context 层维护当前发现的 available contexts，以及用户当前选择。
- 默认选择所有 available contexts；用户可以随时修改当前 Incident 的 context 选择，变更直接作用于当前调查，不存在“下一次调查的 scope selection”。
- 发生有意义的环境变化时，向本次调查追加 change event，并发送消息给 LLM。
- 环境变化本身不自动终结调查，也不自动使历史证据失效。
- 一次调查不绑定 sessionId；Pi SRE 整个应用运行期间使用同一个 `AgentSession` 对象，禁止切换，由运行时入口落实这一约束。结束调查或新建 Incident 都不替换 AgentSession；当前 Incident 的 context 选择仍可随时修改。
- 整个应用运行期间禁止同一 `AgentSession` 对象内的历史导航，关闭 `/tree`、对应快捷键和程序调用；保留滚动和搜索已渲染历史。
- Pi SRE 不允许运行时重新绑定扩展。扩展仅在应用启动时初始化，应用退出时释放；变更扩展需要重启应用。
- 保持只读诊断、每次调用显式提供准确 context、通过 MCP 访问 Kubernetes 的边界。

### 历史 2. 当前实现跟踪的状态

以下是对当前源码的检查结果，并非新设计要求。

| 状态或机制                    | 当前用途                                         | 建议方向                                                                         |
| ----------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------- |
| `sessionId → incidentId` 映射 | 切换 session 后找到对应调查                      | 改为单一当前调查，不绑定 session                                                 |
| `bindingEpoch`                | 区分扩展重新绑定前后的权限                       | 运行时重新绑定扩展不受支持；删除 binding、代次及重新绑定恢复逻辑                 |
| `lifecycleEpoch`              | 开始、结束、取消时使旧执行失效                   | 用具体请求的取消及 incident 身份处理                                             |
| `selectionRevision`           | 标记用户选择版本，拒绝旧选择上的执行             | 更新当前选择并追加事件                                                           |
| `inventoryRevision`           | 标记发现列表版本，拒绝旧 inventory 上的执行      | 替换当前列表并记录有意义的差异                                                   |
| `scopeRevision`               | 标记 incident scope 版本，目前固定为 `1`         | 删除固定版本字段及其一致性校验                                                   |
| `toolsGeneration`             | 确认工具与连接属于同一代                         | 设计存疑：待明确重连后工具与 context 的变化假设，再决定是否收回 MCP 生命周期内部 |
| `workEpoch`、active work 集合 | 防止选择器期间发生工作，以及运行时修改选择       | 删除与 context 选择相关的限制；生命周期所需活动请求跟踪另行保留                  |
| `validatedSelection`          | 区分初始无效选择与曾经有效、当前部分不可用的选择 | 分离启动参数验证与运行时可用性计算                                               |
| `inventoryTransition`         | 保存最近一次 added / removed / changed           | 改为调查中的追加事件列表                                                         |
| execution snapshot / lease    | 将调用绑定到多项状态组合                         | 简化为请求身份、incidentId、实际 context 和取消信号                              |
| `publicationBlocks`           | 工具与 scope 通知发布期间阻止 dispatch           | 评估合并到 MCP ready 状态，避免调查层参与发布协议                                |

主要代码位置：

- [Context manager](../src/cluster/context-manager.ts)：连接版本、inventory 版本、选择版本、快照、工作状态、选择更新限制。
- [Investigation controller](../src/app/investigation-controller.ts)：session 映射、binding、effective scope、lease 与 stale 判断。
- [Context resolver](../src/cluster/context-resolver.ts)：exact/all 规则、选择来源及初始验证与运行时部分可用的区别。

当前 inventory 的 `changed` 包括 server 地址变化和 MCP default 标记变化。Default 标记不决定 Pi SRE 的选择，可以只作为展示元数据；server 变化则可能影响同名 context 的实际指向，适合记录为环境事件。

### 历史 3. 对核心调查流程的影响

#### 历史 3.1. 同时维护本次 scope 与下次选择

当前实现中，Incident 保存不可变 scope rule，context manager 保存用户当前选择；当前调查继续使用前者，用户修改只影响下次调查。

因此 controller、工具发布、状态栏与 LLM 提示均需要处理 `effective / next` 双重状态。已确认的新设计只有当前 Incident 的 context 选择，所有选择变更直接作用于当前 Incident，不保留“下一次调查选择”。可以删除这层转换及其展示逻辑；对已接收请求的处理遵循第 6 节。

参考：[Investigation scope](../src/domain/investigation-scope.ts)、[Investigation controller](../src/app/investigation-controller.ts)、[Cluster extension](../src/tui/cluster-extension.ts)。

#### 历史 3.2. 环境快照决定调用与证据是否有效

`currentScope()` 将 session binding、lifecycle epoch、scope、inventory 与 connection 等拼成 effective scope，并缓存对象。Lease 通过对象身份及连接状态判断是否仍然有效。

因此，即使变化没有影响本次查询的 context，例如 inventory 增加另一个 context，也可能使正在执行的 lease 失效。结果会被标为 stale，无法作为成功证据提交。

新设计建议：应用接收工具调用时，按当时的选择校验目标；校验通过并接收后，固定请求归属与实际 context，包括后续排队等待阶段。用户修改选择不使已接收请求失效，结果按实际请求来源收尾，不再以整个环境快照是否相同作为证据提交条件。具体边界见第 6 节。

参考：[Investigation controller](../src/app/investigation-controller.ts)、[Incident diagnostic](../src/mcp/incident-diagnostic.ts)。

#### 历史 3.3. 技术版本号进入证据领域

Evidence 与 OperationOutcome 都保存 `scopeRevision`、`inventoryRevision`、`connectionGeneration`；工具结果还携带 `selectionRevision`。

建议证据主要保存实际来源、操作、时间、内容与完整性。环境变化由事件解释，不要求每条证据携带环境版本组合。

参考：[Evidence](../src/domain/evidence.ts)、[Investigation state](../src/domain/investigation-state.ts)、[Observation adapter](../src/mcp/observation-adapter.ts)。

#### 历史 3.4. 历史记录受初始 scope 约束

当前聚合验证要求 targets、evidence、outcomes 都属于初始不可变 incident rule，并要求 observation scope revision 与 incident 一致。

允许实时修改选择后，应取消这种历史成员约束。历史记录保留真实来源，即使对应 context 已不在当前选择或 available contexts 中，仍然属于本次调查。

这不取消应用接收新调用时对当前选择和可用性的检查；已接收请求在调用 MCP 前仍需检查运行条件，但不因后来的选择变化而被拒绝。

#### 历史 3.5. 两条诊断调用路径并存

[Tool bridge](../src/mcp/tool-bridge.ts) 同时维护普通 scope snapshot 路径与 incident lease 路径，两者都包含 admission、stale 检查与释放逻辑。

建议统一为一条调用管线，在结果处理后接入调查观察记录。不应仅为保留历史阶段行为而维持两套执行机制。

**已收敛：采用 HolmesGPT 普通 ask/chat 的对话模型，不要求存在活动调查，也不在首次诊断前创建 Incident。** 调用归属于本轮用户请求，结果保存在 messages 与工具结果中，预算按本轮请求管理；具体边界见第 10.8 节。

### 历史 4. 建议的简化模型

```text
当前运行环境
  MCP 状态
  availableContexts
  用户当前选择：all 或 exact set

当前调查
  问题、状态
  evidence、hypotheses、conclusion
  调用记录与预算
  environmentEvents
```

Available contexts 表示 MCP 当前发现的 context 名称，不表示认证成功、集群健康或已经调查。用户选择表示后续新接收调用允许查询的范围，两者仍需区分；修改选择不撤销已接收请求。

默认 `all` 跟随当前 available contexts。用户选定 exact set 后，仅在该集合中查询；列表刷新不应意外扩大用户的 exact 选择。当前可执行集合可以直接由 available contexts 与选择求得，不需要另存一份 incident resolution。

已确认：exact 选择中的 context 从 inventory 消失时，保留为 **unavailable selected**，不自动从选择中删除。执行目标取 exact 选择与当前 available contexts 的交集；完整规则见第 10.9 节。

调查不再保存一份不可变权限 scope。若展示需要，可以保留开始时选择作为历史信息，但不得重新成为执行授权依据。

### 历史 5. 环境事件与 LLM 通知

统一处理流程：

```text
更新当前环境 → 向活动调查追加事件 → 更新 UI → 向 LLM 发送消息
```

适合记录的事件：

- 用户修改当前选择，例如从 `[A, B]` 改为 `[B, C]`。
- Inventory 新增或移除 context。
- 同名 context 的 server 指向发生变化。
- MCP 断开、恢复或被重新启动。

事件记录时间、类型、原因，以及变化前后值或差异即可。不必记录每次内部状态发布，也不必记录内容完全相同的 inventory 刷新。MCP 重连即使 inventory 未变，仍可作为连接恢复事件记录。

事件列表用于解释调查期间发生的变化，不引入事件重放、状态重建或新的事件驱动状态机。没有活动调查时只更新当前环境；开始调查时给出当前环境摘要。

事件记录与 LLM 消息应来自同一个变更事实。调用结果继续保留准确 context，不因通知需要等待下一个模型处理点而混淆来源。上下文压缩后应重新提供当前环境与必要事件摘要，完整事件仍可通过调查检查读取。

当前 [Cluster extension](../src/tui/cluster-extension.ts) 已使用 `pi.sendMessage(..., { deliverAs: "steer" })` 发送 scope 摘要，可复用这条通知机制；当前调查聚合尚没有本文提出的完整环境事件列表。

人决定是否继续调查、重查证据或新建调查；环境事件不自动清空证据、重置预算、终结调查或重新开始。

### 历史 6. 实时修改选择时的调用规则

建议规则：**以应用接收并校验工具调用为边界；新选择影响此后新接收的调用，已接收的只读请求（包括排队中的请求）按原 context 执行并保留结果。**

“已接收”指应用收到一次具体工具调用，按当时的用户选择、工具能力和可用性校验通过，并固定其请求身份、incidentId、实际 context 和必要参数。校验与接收登记之间不得插入异步等待，避免选择在两者之间变化。请求进入应用等待队列后即属于已接收请求，不必等到调用 MCP 接口才获得这一归属。

不以“LLM 何时生成调用”作为边界，因为应用无法可靠判断生成时刻及模型当时看到的选择。即使模型基于旧选择生成调用，只要调用在选择变更后才到达应用，仍按新选择校验；不符合时拒绝，并提供当前允许的范围，不自动改写 context。

示例：应用在选择 A 时接收并校验了对 A 的查询，该请求仍在排队，用户随后改选 B。排队中的请求继续查询 A，返回结果仍保留在原调查中，注明实际 context 和时间；改选后新到达的调用按 B 校验。这样同一次已接收调用不会仅因队列快慢而得到不同的选择校验结果。

```text
应用收到工具调用 → 按当前选择校验并接收 → 排队 → 检查运行条件 → 调用 MCP → 收尾
                  固定请求归属与 context；之后修改选择不撤销该请求
```

- 等待队列中的已接收请求在调用 MCP 前，仍检查取消状态、调查是否仍可接收结果、MCP 就绪状态、工具能力和目标可用性；不再按后来修改的用户选择重新授权。排队不保证调用必定成功。
- 已接收请求保留原 incidentId 与来源，不得把迟到结果归到后来新建的调查，也不得自动替换为新选择的 context。
- 修改选择表示改变后续新接收调用的范围；停止已接收请求通过显式取消表达。活动请求跟踪用于取消、调查生命周期和请求收尾，不用于禁止修改选择。
- 显式取消或 MCP 断开导致请求未完成时，记录失败或取消，不伪装成成功。
- 已确认：调查正常结束时，所有已接收请求均已完成收尾，不存在未完成请求（包括排队请求）；仍有未完成请求时不能宣告调查结束。
- 已确认：调查取消或被替换时，立即取消调查或切换到新调查，并尝试中止旧请求，不等待其完成。取消同时覆盖排队和已派发请求：排队请求不得继续派发，已派发请求尝试通过取消信号中止。
- 取消或替换立即使旧请求失效。即使底层请求无法中止，迟到结果也不得提交为证据、修改调查结论或影响新调查；旧请求只按原 incidentId 完成取消或中断记录及资源释放。
- Server 指向变化通过环境事件明确提示，不把同名 context 的历史观察自动当成新目标的当前事实。

MCP 层仍需拥有连接对象、取消信号、关闭与重连处理，避免旧请求使用新连接或被隐式重放。连接生命周期不必通过 generation 字段扩散到调查领域；是否在 MCP 内部保留 generation，属于实现选择。

**设计存疑：MCP 重连后的工具与 context 假设尚未确定。** 上述收回 MCP 生命周期内部的方向不是已定结论，需要先明确：

- 重连后是否可以假定工具列表、输入 schema 与工具能力不变？若不能，如何重新发现、更新工具，并处理仍使用旧工具定义的调用？
- 重连后是否可以假定 context 列表及同名 context 的 server 指向不变？若不能，如何刷新 inventory、记录变化并检查后续调用目标？
- 工具与 context 的刷新、对外发布及恢复调用之间需要怎样的顺序保证？这些保证是否完全能由 MCP 层承担，还是需要应用层协调？

在这些问题明确前，不据此删除 `toolsGeneration` 或现有重连保护。当前实现仍按既有契约在重连时重新发现工具与 contexts，不假定它们保持不变。

### 历史 7. Session 与扩展生命周期约束

已确认：Pi SRE 整个应用运行期间禁止切换 Pi 的 `AgentSession` 对象，始终使用启动时创建的同一个对象。调查层只维护当前 Incident，不以 sessionId 维护调查映射。当前 Incident 的 context 选择可以随时变化，所有 context 选择变更均作用于当前 Incident，不存在独立的“下一次调查的 scope selection”。

当前生产代码仍会在 `session_start` 时重新 bind，并通过 session 映射查找调查；源码中未见全运行期禁止切换 AgentSession 的入口拦截。因此，“禁止切换”是新设计需要落实的约束，不能当作当前已经具备的保证直接删除 binding。

实施时应拦截会替换当前 `AgentSession` 对象的入口，例如 new、resume、fork、clone、import，以及对应快捷键和程序调用。判定依据是是否替换对象，而非命令名称或仅比较 sessionId。

已确认的独立约束：整个应用运行期间也禁止同一 `AgentSession` 对象内的历史导航，包括 `/tree`、对应快捷键和程序调用；不得打开树选择器，也不得回退历史或切换分支。调查结束后不恢复这些入口。滚动和搜索已渲染历史继续保留。Compaction、context 选择和 MCP reconnect 继续保留。

调查结束后继续使用同一个 `AgentSession` 对象，不恢复任何会话切换入口。通过 `/incident new <question>` 新建 Incident 也在同一个 AgentSession 中进行；新建或结束 Incident 不触发 AgentSession 替换或扩展重新绑定。

已确认的产品约束：Pi SRE 不允许运行时重新绑定扩展。扩展只在应用启动时初始化一次，在退出时清理订阅和资源。`/reload` 及程序调用的扩展 reload/rebind 路径必须被禁止；修改扩展后通过重启应用生效。启动初始化与退出清理无需调查层 binding 或 binding epoch。

因此，新设计不保留扩展代次、旧绑定失效、新绑定恢复调查权限，以及 reload 后重新订阅和重新注入状态等兼容流程。当前实现仍支持相关 Pi 生命周期行为，实施时必须先关闭入口，再移除对应机制。

Compaction 继续保留，不改变调查身份，也不要求重新绑定扩展。MCP reconnect 仅处理连接和工具可用性，使用已经初始化的扩展更新工具，不得触发扩展重建或重新绑定。

参考：[Investigation lifecycle](../src/runtime/investigation-lifecycle.ts)、[Pi runtime](../src/runtime/pi-runtime.ts)、[SRE runtime](../src/runtime/sre-runtime.ts)。

#### 历史 8.1. 已确认：多轮沟通保留调查，显式结束时直接提交

Agent 一次底层运行结束与 Incident 结束是两个独立事件。`agent_end` 只表示一次底层运行结束，之后仍可能有自动恢复或后续工作；它不是调查结束信号。没有未完成查询也只表示当前查询已收尾，不代表调查已有结论或应该结束。

已确认的交互规则：

| 情况                         | Agent 行为                                                                                  | 调查状态                                 |
| ---------------------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------- |
| 已有充分依据解释问题         | 调用 `investigation_conclude`，提交 `resolved` 结论及引用                                   | 校验通过后结束；表示已解释，不表示已修复 |
| 只有假设，还需要用户补充信息 | 可用 `hypothesis_upsert` 保存 `candidate`，在普通回复中说明发现并向用户提问，不调用结束工具 | 保持 `investigating`，保留已有证据和假设 |
| 信息不足，并决定停止本次调查 | 调用 `investigation_conclude`，提交 `inconclusive` 结论并说明限制                           | 校验通过后结束                           |

等待用户通过普通对话表达，不新增 `waiting_for_user` 状态或调查专用提问工具。用户补充信息后继续同一个未结束的 Incident；Agent 可以回顾已有证据、更新假设，必要时重新查询。`inconclusive` 是终态，不用于表示等待用户回答；已结束的调查不因后续补充自动重新打开。

示例：Agent 查询后发现数据库连接等待增加，保存“连接池耗尽”的候选假设，并询问用户最近是否修改连接池配置。本轮 Agent 运行结束，调查仍保持进行中。用户回复“上限从 100 改成了 10”后，Agent 在同一调查中继续分析和验证，不需要新建 Incident。

已确认的提交方向：**Agent 通过 `investigation_conclude` 显式表达结束意图，应用在工具执行时校验并直接提交，不再暂存 pending proposal 或等待 `agent_end`。**

1. 检查当前调查仍在进行中，结论及其证据、假设引用满足领域规则。
2. 检查该调查所有已接收的诊断请求均已完成收尾，包括排队与已派发请求。仍有未完成请求时拒绝本次结束调用，不排队提交；Agent 等待请求收尾后重新调用。
3. 检查与终态写入之间不得插入异步等待；写入后不再接收归属于该已结束调查的新诊断请求。
4. 正式保存结论并返回成功，工具成功即表示调查已经结束，无需下一轮再确认 pending 是否提交。

上述规则与第 6 节的正常结束要求一致。需要继续和用户沟通时不调用结束工具；应用不依据 `agent_end`、查询为空闲或回复中的自然语言自动结束调查。

此前讨论仅取消延迟提交时，调查和 hypothesis revision 的其他用途需要单独评估。第 10 节的新方向已进一步移除调查聚合、Hypothesis 对象及其写入接口，因此不再存在需要这些 revision 保护的领域更新。两者随模型一起移除，不再保留为待定项；这不影响 MCP 内部必要的连接生命周期保护。

当前代码仍采用两阶段提交，以上是后续实施要求，不是当前行为变更。当前实现已经支持通过不调用结束工具来保持调查并进行多轮沟通；尚无专门的等待用户状态。

### 历史 9. 建议优先顺序与待定边界

优先收敛以下机制：

1. 将不可变 incident scope 与 `effective / next` 双状态改为当前选择。
2. 引入调查环境事件列表，复用 LLM steering 通知。
3. 落实第 6 节已确认的在途请求规则，删除基于整个环境版本组合的结果失效逻辑。
4. 落实 session 替换、历史导航和运行时扩展重新绑定的禁令，再移除调查 binding、binding epoch 和 reload 恢复流程。
5. 将连接生命周期收回 MCP 层，统一诊断调用管线。
6. 按第 10 节移除结论提交和调查领域模型，包括调查与 hypothesis revision；多轮沟通由同一对话中的 messages 延续。

已收敛：exact 选择中的 context 消失时保留为 **unavailable selected**，保留用户选择意图，执行目标取当前可用交集；具体行为见第 10.9 节。

已收敛：诊断不依赖活动调查，不由用户或 LLM 创建、识别或切换 Investigation 实体。调用归属、结果保存与预算按第 10.8 节的对话与请求边界处理。

已收敛：调查与 hypothesis revision 不再需要。当前 hypothesis revision 用于旧版本覆盖检查，只保留最新对象，并未保存假设版本历史。新方向不再维护可更新的调查聚合与 Hypothesis 对象，因而无需相应的版本冲突检查；模型根据新证据修正判断直接体现在 messages 中。执行取消、只读校验和连接保护由所属模块负责，不通过领域 revision 承担。

预期结果是：环境变化留下可解释的历史，影响后续调用目标，但不再通过多层 authority、epoch 和 revision 判断来主导核心调查流程。
