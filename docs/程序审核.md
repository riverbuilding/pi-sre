按目前 Phase 5 的计划，程序审核主要检查“调用是否符合安全边界、目标是否明确、参数是否能安全展示给用户”，不判断这个操作能不能修好故障。

其中，ControlledCallReview 计划负责这些内容：

| 审核项             | 具体要求                                                             |
| ------------------ | -------------------------------------------------------------------- |
| 资源类型           | 初期只允许命名空间内的 Pod、Deployment、StatefulSet                  |
| 禁止敏感或扩权资源 | 拒绝 Secret、RBAC、CRD、Namespace、Node、准入配置等资源              |
| 目标身份明确       | 必须能得到明确的 apiVersion、kind、namespace、name，不能依赖生成名称 |
| 目标范围一致       | Manifest 不能指定另一个 namespace/context，绕过本次调用的目标范围    |
| 危险配置           | 拒绝特权模式、主机访问、hostPath 挂载等配置                          |
| 凭据与敏感内容     | 不允许引入凭据材料；如果无法安全、完整地展示最终参数，就拒绝提议     |
| Manifest 无歧义    | 只接受单个对象；拒绝多文档、重复键、会掩盖身份的别名等输入           |

审核通过后，返回准确的资源身份；不通过则抛异常。依据见 Phase 5 安全策略约定 (docs/PHASE5_CONTRACTS.md:173) 和 调用身份约定 (docs/PHASE5_CONTRACTS.md:234)。

外围的 ControlledApprovalService 还会做通用检查，这些不全属于 ControlledCallReview：

- 是否启动了受控模式，且配置允许这个工具。
- 参数是否符合 MCP 发现的 input schema。
- 是否显式指定了允许且可用的 context。
- 人工批准前后，参数、选择范围、连接、工具描述和策略是否保持有效。
- 审批是否过期、请求是否取消、执行预算是否足够。

计划不要求程序审核操作的业务效果，例如：

- 删除 Pod 是否能解决故障。
- 扩容到 3 个副本是否合理。
- Apply 会产生哪些完整差异或关联影响。
- 操作后是否恢复健康。

这些由用户和模型结合诊断信息判断，Kubernetes 负责完整资源校验。

目前 Slice 4 已完成通用审批基础设施，Slice 5 的具体参数审核策略还没接入生产。因此，上面是已经约定的审核范围，具体字段级规则仍需要 Slice 5 实现和测试。
